# concurrent-sessions Specification

## Purpose
Правила одновременной работы нескольких пользователей: чей-то долгий шаг не должен останавливать бота для
остальных, ответы одного пользователя не должны попадать другому, а хранилище обязано выдерживать одновременные
записи.
## Requirements
### Requirement: Долгий шаг одного пользователя не задерживает других

Обработка сообщений и нажатий разных пользователей SHALL идти независимо (апдейты обрабатываются конкурентно). Пока
для одного пользователя выполняется длительный шаг (запрос к агенту, работа с клоном репозитория), сообщения других
пользователей SHALL приниматься и обрабатываться, а не ждать его завершения.

#### Scenario: Второй пользователь пишет во время долгого шага первого

- **WHEN** для одного пользователя идёт ответ Справки, занимающий десятки секунд, и в это время другой пользователь
  отправляет `/echo`
- **THEN** второй пользователь получает ответ, не дожидаясь окончания шага первого

#### Scenario: Бот продолжает получать обновления

- **WHEN** для одного пользователя идёт длительный шаг
- **THEN** бот продолжает принимать входящие обновления, и после освобождения ни одно из пришедших за это время
  сообщений не потеряно

### Requirement: Блокирующие операции не останавливают обработку

Операции, которые ждут диск, сеть или внешний процесс - клонирование и обновление клона `TGBOT_REPO_URL`, чтение
файлов инструментами агента, построение обзора файлов, чтение журнала для `/logs` - SHALL выполняться вне цикла
событий и SHALL NOT останавливать обработку сообщений других пользователей на время своего выполнения.

#### Scenario: Обновление клона репозитория

- **WHEN** у одного пользователя ответ Справки требует обновления клона и эта операция длится до своего таймаута
- **THEN** остальные пользователи в это время продолжают получать ответы

#### Scenario: Недоступный источник репозитория

- **WHEN** обновление клона завершается ошибкой или таймаутом
- **THEN** Справка этого пользователя отвечает на имеющихся данных, а остальные пользователи ошибки не замечают

### Requirement: Ответ агента не переходит между пользователями

Сохранённый ответ агента SHALL быть доступен повторно только тому пользователю, для запроса которого он был получен:
пользователь входит в ключ кэша. Совпадение текста запроса у разных пользователей SHALL NOT приводить к выдаче чужого
ответа.

#### Scenario: Одинаковые вопросы у двух пользователей

- **WHEN** два пользователя задают Справке один и тот же вопрос
- **THEN** каждый получает результат, полученный по его собственному запросу

#### Scenario: Повторный вопрос того же пользователя

- **WHEN** тот же пользователь повторяет вопрос с тем же промптом в пределах срока кэша
- **THEN** сохранённый ответ переиспользуется

### Requirement: Хранилище выдерживает одновременный доступ

Одновременная работа нескольких пользователей SHALL NOT приводить к ошибкам доступа к хранилищу и к потере
записанных данных. Соединение SQLite общее и используется только из цикла событий; в рабочие потоки уходит только
работа, которая БД не трогает (git, чтение файлов).

#### Scenario: Одновременная запись от нескольких пользователей

- **WHEN** несколько пользователей одновременно проходят шаги, записывающие сессию и журнал
- **THEN** все записи сохранены, ни один шаг не завершается ошибкой доступа к хранилищу

#### Scenario: Перезапуск при нескольких открытых сессиях

- **WHEN** бот перезапускается, пока у нескольких пользователей открыты сессии режимов
- **THEN** каждая сессия продолжается со своего шага, сессии не перемешаны
