# access-control Specification

## Purpose
Ограничивает доступ к боту разрешёнными пользователями и даёт администратору управлять этим списком прямо из бота, без правки конфигов на сервере.

## Requirements

### Requirement: Бот работает только в личных чатах
Бот SHALL обрабатывать сообщения только из личных чатов (private). Сообщения из групп и каналов SHALL игнорироваться без ответа.

#### Scenario: Бота добавили в групповой чат
- **WHEN** боту приходит сообщение или команда из группового чата
- **THEN** бот не отвечает и не создаёт сессию

### Requirement: Доступ по allowlist
Бот SHALL принимать команды только от пользователей из allowlist (хранится персистентно). Пользователю не из allowlist бот SHALL ответить отказом ровно один раз за диалог и далее молчать - бот нельзя использовать как эхо. Текст отказа SHALL содержать подсказку отправить заявку на доступ командой `/request_access`.

#### Scenario: Неизвестный пользователь пишет боту
- **WHEN** пользователь, которого нет в allowlist, отправляет любое сообщение
- **THEN** бот отвечает одним сообщением, что бот доступен только разрешённым пользователям и заявку на доступ можно отправить через `/request_access`, и не отвечает на последующие сообщения этого пользователя

#### Scenario: Разрешённый пользователь начинает работу
- **WHEN** пользователь из allowlist пишет вопрос
- **THEN** бот отвечает Справкой

### Requirement: /whoami работает до проверки доступа
Команда `/whoami` SHALL отвечать `user_id` и `chat_id` любому пользователю, включая тех, кого нет в allowlist. Это единственная команда до проверки; ничего, кроме двух идентификаторов, она не сообщает.

#### Scenario: Неизвестный пользователь запрашивает /whoami
- **WHEN** пользователь не из allowlist отправляет `/whoami`
- **THEN** бот отвечает его `user_id` и `chat_id`

### Requirement: Администратор управляет allowlist из бота
Пользователи, перечисленные в переменной окружения `ADMIN_USER_IDS` (корень доверия, из бота не изменяется), SHALL иметь команды добавления и удаления разрешённых пользователей и просмотра списка. Изменения SHALL применяться немедленно, переживать рестарт и записываться в журнал (кто, кого, когда).

#### Scenario: Админ добавляет пользователя
- **WHEN** админ отправляет команду добавления с `user_id`
- **THEN** пользователь появляется в allowlist, бот подтверждает, запись попадает в журнал

#### Scenario: Админ удаляет пользователя
- **WHEN** админ отправляет команду удаления с `user_id`
- **THEN** пользователь исчезает из allowlist и при следующем сообщении получает отказ

#### Scenario: Не-админ пытается управлять списком
- **WHEN** пользователь из allowlist, но не из `ADMIN_USER_IDS`, отправляет админ-команду
- **THEN** бот отвечает отказом и allowlist не меняется

### Requirement: Режим "только для админов"
Копия бота для одного человека SHALL включать режим "только для админов" настройкой `TGBOT_OWNER_ONLY=1`. В этом режиме бот SHALL пускать только пользователей из `ADMIN_USER_IDS`: записи allowlist не дают доступа, остальным бот SHALL NOT отвечать даже отказом, событие отказа в журнал пишется как обычно. `/whoami` SHALL работать по-прежнему: им узнают свой `user_id`. Режим с пустым `ADMIN_USER_IDS` SHALL ронять старт с ошибкой конфигурации: иначе ботом не смог бы пользоваться никто.

#### Scenario: Админ пишет в режиме "только для админов"
- **WHEN** режим включён, и пользователь из `ADMIN_USER_IDS` задаёт вопрос
- **THEN** бот отвечает как обычно

#### Scenario: Пользователь из allowlist в режиме "только для админов"
- **WHEN** режим включён, и пользователь из allowlist, но не из `ADMIN_USER_IDS`, отправляет сообщение
- **THEN** бот не отвечает, в журнале есть событие отказа

#### Scenario: Режим без админов
- **WHEN** `TGBOT_OWNER_ONLY=1`, а `ADMIN_USER_IDS` пуст
- **THEN** старт падает с ошибкой конфигурации, называющей `ADMIN_USER_IDS`
