# file-logging Specification

## Purpose
Файловые логи всего происходящего в боте - по файлу на сессию (сессию режима или диалог Справки), с полными текстами обмена с LLM и ротацией по суммарному размеру каталога - для разбора инцидентов и оценки качества без доступа к SQLite.

## Requirements

### Requirement: Файл лога на сессию

Каждое событие журнала, относящееся к сессии, SHALL дописываться строкой JSONL в файл этой сессии в каталоге логов (`TGBOT_LOGS_DIR`, дефолт `./logs`); события вне сессий SHALL писаться в общий файл. Свой файл SHALL быть у каждой сессии режима (вход в режим - новый файл) и у диалога Справки - чтобы каждый открывался отдельной строкой в `/logs`. Имя файла сессии SHALL позволять найти сессию по времени старта и пользователю.

#### Scenario: Событие сессии

- **WHEN** в журнал пишется событие с известной сессией (вопрос, ответ, выбор, шаг режима)
- **THEN** строка с временем, видом события и payload дописана в файл этой сессии

#### Scenario: Событие вне сессии

- **WHEN** пишется событие без сессии (отказ в доступе, админ-команда, старт бота)
- **THEN** строка дописана в общий файл логов

#### Scenario: Ошибка записи не ломает бота

- **WHEN** запись в файл невозможна (нет места, нет прав)
- **THEN** событие остаётся в SQLite-журнале, диалог продолжается; исключение не пробрасывается

#### Scenario: Диалог Справки

- **WHEN** пользователь без открытого режима задаёт вопрос обычным текстом
- **THEN** вопрос, вызов модели и ответ дописаны в файл журнальной сессии Справки, а не в общий файл

### Requirement: Полные тексты LLM-обмена

Каждый запрос к LLM SHALL логироваться полным списком сообщений, которые ушли модели (системный промпт, история, текст пользователя), и списком предложенных инструментов. Каждый ответ SHALL логироваться полным текстом, провайдером, моделью и признаком кэш-попадания; когда провайдер отдаёт стоимость/usage, они SHALL включаться в запись. Каждый вызов инструмента агентом SHALL логироваться отдельным событием: имя инструмента, аргументы, полный результат, который ушёл модели, и длительность. Это касается всех вызовов агента: полный и облегчённый ответ Справки, повтор по "Не понятно" и распознавание скриншота.

#### Scenario: Запрос и ответ

- **WHEN** бот вызвал LLM (любую модель лестницы) и получил ответ
- **THEN** в лог сессии записаны событие запроса со всеми сообщениями и событие ответа с полным текстом, провайдером и моделью

#### Scenario: Кэш-попадание

- **WHEN** ответ взят из кэша без обращения к LLM
- **THEN** записано событие ответа с признаком кэша, без события запроса к провайдеру

#### Scenario: Вызов инструмента

- **WHEN** модель во время ответа попросила прочитать файл или поискать по коду
- **THEN** в журнале есть событие вызова инструмента с аргументами и полным результатом, в порядке, в котором они шли в обмене

### Requirement: Ротация по суммарному размеру

Когда суммарный размер каталога логов превышает лимит (`TGBOT_LOGS_MAX_BYTES`, дефолт 1 ГБ), старейшие файлы SHALL удаляться до возвращения под лимит; файлы идущих сессий (открытая сессия режима и сессия Справки) SHALL NOT удаляться.

#### Scenario: Лимит превышен

- **WHEN** суммарный размер файлов каталога превысил лимит
- **THEN** старейшие по времени изменения файлы удалены, суммарный размер снова под лимитом

#### Scenario: Активная сессия защищена

- **WHEN** ротация запущена, а старейший файл принадлежит открытой сессии режима или Справки
- **THEN** этот файл пропускается, удаляются следующие по старшинству

### Requirement: Завершённая сессия не забирает последующие события

Событие без явной сессии SHALL зеркалиться в файл текущей сессии пользователя - открытой сессии режима или сессии
Справки, которую открыл последний вопрос. Когда сессия режима закрыта, она SHALL NOT забирать последующие события:
они идут в файл следующей открытой сессии, а без неё - в общий файл бота. Выбор файла SHALL NOT делать запрос к БД на
каждое событие.

Событие с явной сессией SHALL попадать в её файл независимо от статуса.

#### Scenario: Событие после выхода из режима

- **WHEN** пользователь вышел из `/echo`, и у него нет сессии Справки, а затем отправил `/help`
- **THEN** событие команды попадает в общий файл бота
- **AND** файл закрытой сессии Эхо его не получает

#### Scenario: Событие в открытом режиме

- **WHEN** событие без явной сессии происходит при открытой сессии режима
- **THEN** оно попадает в файл этой сессии

#### Scenario: Явная сессия

- **WHEN** событие несёт явную сессию
- **THEN** оно попадает в файл этой сессии независимо от её статуса

#### Scenario: У пользователя сессий не было

- **WHEN** событие происходит у пользователя без единой сессии
- **THEN** оно попадает в общий файл бота

### Requirement: Входящие апдейты целиком

Каждый апдейт, полученный ботом от Telegram, SHALL записываться в файловый журнал целиком, до любой фильтрации и проверки доступа: любой тип чата (личный, группа, супергруппа, канал) и любой тип апдейта (сообщение, правка, нажатие кнопки, картинка, документ, изменение участников). Вложения SHALL описываться метаданными (идентификатор файла, имя, размер, тип), содержимое файла не пишется. Событие SHALL попадать в файл активной сессии пользователя, иначе в общий файл, по тем же правилам, что и остальные события.

#### Scenario: Сообщение в личке

- **WHEN** пользователь пишет боту текст в личном чате
- **THEN** в журнале есть событие входящего апдейта с полным текстом, `chat_id`, типом чата и `user_id`

#### Scenario: Сообщение из группы

- **WHEN** апдейт пришёл из группового чата, который бот игнорирует
- **THEN** апдейт всё равно записан в журнал, хотя ответа на него нет

#### Scenario: Отказ в доступе

- **WHEN** пишет пользователь вне allowlist
- **THEN** его апдейт записан в журнал целиком, вместе с событием отказа

#### Scenario: Нажатие кнопки и картинка

- **WHEN** пользователь нажимает кнопку или присылает картинку с подписью
- **THEN** записаны `callback_data` нажатия или подпись и метаданные картинки

### Requirement: Исходящие вызовы Bot API целиком

Каждый вызов Bot API, кроме получения апдейтов, SHALL записываться в файловый журнал: имя метода, все параметры (текст, разметка, кнопки, `chat_id`, `message_id`) и результат вызова или ошибка. Это касается всех методов: отправки, правки и удаления сообщений, отправки документов, ответа на нажатие, реакций, меню команд. Содержимое текстового документа (`.md`, `.txt`, `.json`, `.jsonl`) SHALL записываться полностью. Для двоичного документа пишутся имя и размер.

#### Scenario: Ответ текстом

- **WHEN** бот отправляет или правит сообщение
- **THEN** в журнале есть событие исходящего вызова с методом, полным текстом, кнопками и `message_id` из результата

#### Scenario: Отправка `.md`

- **WHEN** бот отправляет `.md`-файл (журнал через `/logs`, части длинного файла)
- **THEN** в журнале записаны имя файла, подпись и полный текст файла

#### Scenario: Вызов не удался

- **WHEN** Bot API вернул ошибку (неверная разметка, сообщение не найдено)
- **THEN** записаны параметры вызова и текст ошибки, а бот ведёт себя как раньше

### Requirement: Обмен с моделью распознавания скриншотов

Каждый запрос бота к модели распознавания скриншотов SHALL записываться в журнал вместе с ответом: модели, промпт,
полный ответ модели или причина сбоя (ошибка, таймаут). Картинка SHALL описываться размером, форматом и хешем, её
байты не пишутся.

#### Scenario: Распознавание скриншота

- **WHEN** бот отправляет картинку на распознавание
- **THEN** записаны модель, размер и хеш картинки, промпт и полный ответ модели

### Requirement: Секреты не попадают в журнал

Токен бота, ключи API и заголовки авторизации NOT SHALL попадать ни в одно событие журнала: адрес Bot API пишется без токена, заголовки запросов не пишутся, строки вида токена или ключа заменяются меткой.

#### Scenario: Исходящий вызов

- **WHEN** записывается исходящий вызов Bot API
- **THEN** в событии есть имя метода, но нет адреса с токеном

#### Scenario: Ключ в тексте

- **WHEN** пользователь прислал текст, в котором есть строка вида ключа API
- **THEN** в журнале на её месте метка, остальной текст сохранён

### Requirement: Вопрос Справки в журнале целиком, с входящего апдейта

Когда пользователь с доступом присылает в личный чат свободный текст без открытой сессии режима, файл сессии Справки
SHALL быть выбран до записи входящего апдейта. В этот файл SHALL попадать входящий апдейт, реакция "принято", подсказка
о смене языка, событие её показа и все дальнейшие события ответа. Новая сессия SHALL открываться по тем же правилам, что
сейчас (истёк контекст диалога Справки - новая, иначе продолжается текущая), и SHALL NOT открываться повторно на тот же
вопрос. Команды, нажатия кнопок и сообщения других пользователей и чатов SHALL NOT открывать сессию Справки.

#### Scenario: Первое сообщение нового диалога

- **WHEN** пользователь без активного диалога Справки пишет по-английски при русском интерфейсе
- **THEN** в файле новой сессии Справки первым идёт входящий апдейт, за ним - реакция, подсказка о смене языка и событие `language_offer` (между собой в любом порядке), затем вопрос и ответ
- **AND** в общем файле этих событий нет

#### Scenario: Одна сессия на вопрос

- **WHEN** первый вопрос нового диалога записан в журнал
- **THEN** для него открыта ровно одна сессия Справки

#### Scenario: Команда не открывает Справку

- **WHEN** пользователь без активной сессии отправляет `/logs`
- **THEN** апдейт пишется в общий файл, сессия Справки не открывается
