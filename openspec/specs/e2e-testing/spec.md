# e2e-testing Specification

## Purpose

Проверка бота целиком, а не по хендлерам: слой Bot API ловит ошибки сериализации, маршрутизации апдейтов и разметки без сети, слой True E2E подтверждает, что настоящий процесс бота работает с настоящим Telegram.

## Requirements

### Requirement: Слой Bot API идёт в каждом прогоне тестов

Репозиторий SHALL содержать набор тестов, в котором приложение бота собирается тем же кодом, что и в проде, и общается по HTTP с локальным фейковым Bot API вместо `api.telegram.org`. Тест SHALL подавать боту апдейты в формате JSON Bot API и проверять вызовы методов Bot API, которые бот сделал в ответ, с их параметрами. LLM SHALL заменяться локальной HTTP-заглушкой. Набор SHALL NOT обращаться в сеть и SHALL NOT требовать секретов; он SHALL запускаться обычной командой `pytest` вместе с остальными тестами.

#### Scenario: /start через настоящее приложение

- **WHEN** фейковый Bot API отдаёт апдейт с сообщением `/start` от разрешённого пользователя
- **THEN** бот вызывает `sendMessage` в этот чат с приветствием на языке пользователя, и тест видит этот вызов

#### Scenario: Нажатие инлайн-кнопки

- **WHEN** фейковый Bot API отдаёт `callback_query` с данными кнопки, которую бот сам прислал раньше
- **THEN** бот отвечает `answerCallbackQuery` на этот запрос и реагирует на кнопку тем же, что в живом Telegram

#### Scenario: Ошибка Bot API на разметке

- **WHEN** фейковый Bot API отвечает на `sendMessage` с `parse_mode=HTML` ошибкой разбора сущностей
- **THEN** бот повторяет отправку без разметки, и пользователь получает текст

#### Scenario: Тест без сети

- **WHEN** набор запускается на машине без доступа в интернет и без переменных с ключами
- **THEN** все тесты слоя проходят

### Requirement: Слой True E2E проверяет живой бот в тестовом окружении Telegram

Репозиторий SHALL содержать отдельный набор сценариев (`tests_e2e/`, Telethon), в котором настоящий процесс бота (`python -m tgbot`) работает с Telegram под отдельным тестовым ботом, а сценарии ведёт скриптованный аккаунт пользователя. По умолчанию это тестовое окружение Telegram (`E2E_TELEGRAM_ENV=test`); `E2E_TELEGRAM_ENV=prod` - отдельный тестовый бот и запасной аккаунт в обычном Telegram. Секреты набор SHALL читать из `.env.e2e` в корне репозитория (или из файла `E2E_ENV_FILE`), окружение процесса сильнее: `E2E_API_ID`, `E2E_API_HASH`, `E2E_SESSION`, `E2E_BOT_TOKEN`, `E2E_BOT_USERNAME`. Набор SHALL NOT входить в обычный прогон `pytest` и SHALL запускаться явной командой. Перед стартом бот SHALL сбрасывать накопленные апдейты прошлых прогонов. Без нужных секретов набор SHALL пропускаться с понятной причиной, а не падать. Набор SHALL NOT использовать токен прод-бота (`TELEGRAM_BOT_TOKEN`) и прод-аккаунты. Сценарии SHALL идти последовательно; каждый сценарий SHALL начинать с известного состояния пользователя. LLM SHALL заменяться локальной заглушкой, чтобы прогон не зависел от внешнего провайдера и не стоил денег.

#### Scenario: Запуск без секретов

- **WHEN** набор True E2E запускается без любой из переменных `E2E_API_ID`, `E2E_API_HASH`, `E2E_SESSION`, `E2E_BOT_TOKEN`, `E2E_BOT_USERNAME`
- **THEN** все сценарии помечаются пропущенными с указанием недостающей переменной

#### Scenario: Сквозной /start

- **WHEN** тестовый пользователь пишет тестовому боту `/start`
- **THEN** в течение таймаута приходит ответ бота с ожидаемым текстом, отрисованный Telegram: разметка видна как форматирование, а не сырыми тегами

#### Scenario: Сценарий с правкой сообщения

- **WHEN** тестовый пользователь нажимает инлайн-кнопку в ответе бота
- **THEN** бот правит сообщение или присылает новое, и тест видит результат так, как его видит человек

#### Scenario: Защита от прода

- **WHEN** id бота в `E2E_BOT_TOKEN` совпадает с id бота в `TELEGRAM_BOT_TOKEN` из окружения или из `.env` (перевыпущенный токен - тот же прод-бот)
- **THEN** набор отказывается запускаться

### Requirement: Сессия тестового пользователя создаётся один раз

Репозиторий SHALL содержать скрипт, который интерактивно входит в аккаунт тестового окружения Telegram и печатает строку сессии для хранения как секрета. Скрипт SHALL NOT сохранять сессию в файлах репозитория.

#### Scenario: Первый вход

- **WHEN** человек запускает скрипт с `api_id` и `api_hash` и вводит номер тестового аккаунта и код
- **THEN** скрипт печатает строку сессии, и с ней набор True E2E входит без повторного ввода кода

### Requirement: Слой Bot API покрывает роли и режимы

Слой Bot API SHALL проверять каждую команду и свободный текст под каждой ролью: админ, разрешённый пользователь, пользователь вне allowlist, пользователь, снятый через `/deny`, и групповой чат. Слой SHALL проверять режимы (Справка, `/echo`, `/start`) и переходы между ними, распознавание намерения пользователя и одновременную работу нескольких пользователей разных ролей.

#### Scenario: Чужой пользователь

- **WHEN** пользователь вне allowlist шлёт рабочую команду, а затем ещё одно сообщение
- **THEN** первый раз он получает отказ с подсказкой про `/request_access`, второй раз бот молчит, а `/whoami` и `/request_access` ему отвечают

#### Scenario: Эхо и выход в Справку

- **WHEN** разрешённый пользователь входит в `/echo`, пишет два текста и нажимает "Выйти в Справку"
- **THEN** оба текста возвращены эхом с шагами 1 и 2, а следующий текст уходит в Справку

#### Scenario: Состояния пользователей не смешиваются

- **WHEN** два пользователя одновременно задают Справке вопросы, а админ в это время решает заявку на доступ
- **THEN** каждый получает свой ответ, и ни одно сообщение не уходит не тому пользователю
