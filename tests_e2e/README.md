# True E2E

Настоящий процесс бота работает с **тестовым окружением Telegram**, сценарии
ведёт аккаунт пользователя через Telethon. LLM - локальный фейк
(`tests/fakes`), поэтому прогон бесплатный и от провайдера не зависит.

Запуск: `deploy/e2e.sh` (аргументы уходят в pytest, например `-k support`).
Без секретов все сценарии пропускаются с именем недостающей переменной; с
токеном, совпавшим с прод-`TELEGRAM_BOT_TOKEN`, набор отказывается стартовать.

## Где живёт тестовый бот: два режима

| `E2E_TELEGRAM_ENV` | Бот | Пользователь | Когда |
|---|---|---|---|
| `test` (по умолчанию) | бот тестового DC (@BotFather внутри тестового аккаунта) | тестовый аккаунт `99966XYYYY`, SIM не нужна | шаги ниже |
| `prod` | отдельный бот у обычного @BotFather (не прод-бот!) | **запасной** настоящий аккаунт, не основной | бот уже создан в обычном Telegram |

В режиме `prod` бот и аккаунт живут в настоящем Telegram, поэтому:
- бот - только отдельный тестовый; совпадение id с прод-ботом набор отклонит;
- аккаунт - запасной: под автоматизацией и на нём админ тестового бота;
- сессия: `make_session.py --prod` (код придёт в приложение Telegram,
  при облачном пароле скрипт его спросит).

## Однократная настройка (режим `test`)

Тестовое окружение - отдельные серверы Telegram со своими аккаунтами и
ботами; прод не затрагивается. Telegram периодически стирает его данные - тогда
шаги 1-4 повторить.

1. **Тестовый аккаунт.** Номер `99966XYYYY`: X - номер DC (1-3, по умолчанию
   2), YYYY - любые цифры. SIM не нужна, код входа - X пять раз (`22222`).
   На номер около 5 входов в сутки - при лимите смените YYYY.
   Зарегистрировать можно только в официальном клиенте (Telethon 1.x
   `sign_up` не умеет):
   - Telegram Desktop: Settings -> Shift+Alt+правый клик по "Add Account" -> Test Server;
   - iOS: 10 раз нажать на значок Settings -> Accounts -> Login to another account -> Test;
   - macOS: 10 раз нажать на Settings, затем ⌘+клик по "Add Account".
2. **Тестовый бот.** В том же клиенте, под тестовым аккаунтом: @BotFather ->
   `/newbot`. Токен - в `E2E_BOT_TOKEN`, имя `@...` - в `E2E_BOT_USERNAME`.
3. **api_id / api_hash** с https://my.telegram.org (подходят и для тестового
   DC; там же в "test configuration" видны адреса тестовых DC - сверьте с
   `TEST_DC_IP` в `make_session.py`).
4. **Сессия:**
   ```
   uv run --extra e2e python tests_e2e/make_session.py --api-id <id> --api-hash <hash> --dc 2
   ```
   Напечатанную строку - в `E2E_SESSION`.
5. **Второй аккаунт (по желанию)** - для сценария "чужой пользователь":
   шаги 1 и 4 для другого номера, строку - в `E2E_SESSION_2`.

## На сервере (`/opt/tg-bot`)

Каталог принадлежит пользователю сервиса, и в нём работает прод-бот.
`deploy/e2e.sh` туда ничего не пишет: свой venv - `~/.cache/tg-bot-e2e/venv`
(или `E2E_VENV`), проект не ставится, `__pycache__` не создаётся. Секреты
держите у себя, а не в `/opt`:

```
E2E_ENV_FILE=~/.config/tg-bot-e2e.env /opt/tg-bot/deploy/e2e.sh
```

Тестовый бот - отдельный токен тестового DC: прод-бот на том же сервере ему
не мешает (у них разные серверы Telegram), а совпадение с прод-токеном набор
отклонит.

## `.env.e2e` (в корне репозитория или по пути `E2E_ENV_FILE`, в git не попадает)

```
E2E_API_ID=
E2E_API_HASH=
E2E_SESSION=
E2E_BOT_TOKEN=
E2E_BOT_USERNAME=@my_test_bot
# test (по умолчанию) или prod
E2E_TELEGRAM_ENV=test
# E2E_SESSION_2=
```

## Что проверяется

Только то, что видно в живом Telegram: отрисовка HTML (нет сырых тегов,
есть сущности), меню команд, правки и новые сообщения после нажатий,
длинные ответы по частям, заявка на доступ. Полная матрица ролей и режимов - в слое Bot API (`tests/botapi`),
он идёт в каждом `pytest`.
